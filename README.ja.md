# SigmaOmega — フィードバック制御シミュレーター

[English](README.md) | 日本語

SigmaOmega は、ブラウザで動くフィードバック制御系のシミュレーターです。名前はラプラス変換の *s* = σ + *j*ω に由来します（保存した設定・ファイル・リンクがそのまま使えるよう、プログラムとブラウザの保存領域では以前の短い名前 `ctrlsim` を使い続けます）。公開するページは `index.html` 1 ファイルで完結しています（数式表示に MathJax を CDN から読み込みます）。このファイルは `src/` のソースからビルドします。

## 主な機能

- ヘッダーの下の濃い色のメニューバーにすべてのメニュー（ファイル、表示する図、系の設定、解析・設計、図の並び方、指標の表示）を線のアイコン付きで配置。開いているメニューとカードを表示しているメニューには赤い下線。その下の設定パネルは「ファイル」「系の設定」「解析・設計」のメニューから選んだカードを1枚ずつ表示し、細い帯に折りたたみ可能（≪）。指標はカードと表形式を切り替え可能。スマートフォンでは画面下のバーで設定と図を切り替え
- アプリの中の利用者マニュアル：メニューバー右端の「使い方」で開く（11 の章と目次。4 つの演習を手順どおりに説明する章を含む。日本語と英語）
- 制御対象：6 種類のプリセット、または伝達関数を直接入力（むだ時間を含む）
- 制御器：P / PI / PD / PID、位相進み・位相遅れ・位相進み遅れ補償、または伝達関数を直接入力
- 目標値：ステップ・ランプ・放物線・台形・パルス・矩形波・正弦波
- 外乱・観測ノイズ・操作量の飽和（アンチワインドアップ）
- 時間応答と応答指標、ボード線図（ゲイン余裕・位相余裕。周波数範囲は自動または手動で、極・零点・むだ時間・シミュレーション時間が変わると自動に戻る）、ナイキスト線図、極・零点配置（閉ループ極の一覧）
- 根軌跡（ループゲインを k 倍）：マウスを重ねて値を表示、クリックでゲインを適用、安定となる k の範囲、ζ・ωn の格子
- 外乱からの応答：Gyd = P/(1+L)・Gyr = Cr P/(1+L) のボード線図、外乱ゲインの最大値、最大変動と回復時間。目標値の重み b、c をもつ 2自由度 PID（ブロック線図は u = Cr(s) r − C(s) y の形に切り替え。操作量の飽和・外乱 d・ノイズ n は使うときだけ表示し、その分ブロック線図を短く描く）
- 結果の書き出し：各グラフのデータを CSV（掃引を含む時間応答、L・P・C・S・T・Gyd・Gyr の周波数応答、ナイキスト線図、極・零点）で、各グラフを PNG 画像で保存
- 例題（シナリオ）：すべての設定を名前と課題文付きでブラウザや .json ファイルに保存、テキストやリンクとしてコピーして学生に配布、読み込み（レイアウトも一緒に保存・再現可能）。演習の例題を3つ収録
- 感度関数 S(jω)・相補感度関数 T(jω) のボード線図、最大感度 Ms、Mt、閉ループ帯域幅、ナイキスト線図上の半径 1/Ms の円、設計仕様としての Ms
- パラメータの掃引：制御対象・制御器のパラメータを最大8個の値に変えた結果をすべての図に重ね、オーバーシュート、整定時間、安定余裕、安定性、仕様の判定を表で比較
- チューニング則による PID の自動調整（ジーグラ・ニコルスのステップ応答法・限界感度法、CHR、IMC）：同定したモデルとゲインを表示し、ボタン1つで適用
- 設計仕様（オーバーシュート、整定時間、立ち上がり時間、定常偏差、位相余裕、ゲイン余裕、減衰係数 ζ）：✓/✗ の判定、グラフ上の限界表示、極・零点配置図の設計領域、極の仕様を満たす根軌跡上の k の範囲
- ブロック線図はほかの図と同じ区画：1列・2列・横一列では上段に全幅、自由な配置ではどこにでも置ける（左右にグラフ、幅は列の境界で変更）。区画の下端で高さを変え、図は区画の幅を超えない
- すべての区画（図、ブロック線図、伝達関数）の見出しの右端に × があり、押すとその区画を非表示にする（「表示する図」で外すのと同じ）。最後の 1 つの区画は非表示にできない
- 伝達関数 C(s)・P(s) はほかの図と同じ区画として表示（最初は時間応答の横）。区画の下端をドラッグすると高さが変わり、高さに合わせて式が拡大縮小（区画の幅いっぱいまで。幅が足りなくなると自動で縮めて表示）
- ループの伝達関数 L(s)・S(s)・T(s)・G_yr(s)・G_yd(s) を表示する区画（「表示する図」の「ループの伝達関数」）。区画のボタンで表示する式を選び、それぞれ定義と、数値を入れた有理式で表示する（むだ時間は e^(−Ls) のまま、共通因子は約分しない）。区画の下端で、伝達関数の区画と同じように式を拡大縮小できる（大きさは別々に記憶）
- P(s)・C(s)・L(s)・S(s)・T(s)・G_yr(s)・G_yd(s) の極を表示する区画（「表示する図」の「極」）。区画のボタンで伝達関数を選び、極を ζ・ωn・ωd・時定数とともに表で示す（右半平面の極は赤。むだ時間があるとき閉ループの極は 3 次の Padé 近似による）
- 区画を行に並べ、行ごとに横に並べる数を変えられる（並べ方「行」：たとえばブロック線図だけの行、2 つの図の行、3 つの図の行。同じ行の区画は一番高いものに高さをそろえる）。⠿ をドラッグして別の行や新しい行へ移し、行の中の区画の境界をドラッグして幅を変える
- 表示する図をプルダウンメニューで複数選び（各図にチェック）、1列・2列・横一列に並べるか、自由に配置して表示。自由な配置では、図の ⠿ をドラッグして（矢印キーでも）列の中・別の列・新しい列へ移動し、列の境界をドラッグして幅を変更（ブラウザに記憶）。領域の下端をドラッグすると高さが変わり、中のグラフは同じ比率で拡大縮小。すべてのグラフで拡大縮小・表示域の移動（ホイール、ドラッグ、ダブルクリックで元に戻す）
- 表示領域のサイズ変更・表示／非表示（ブラウザに保存）
- 多言語対応：日本語・英語・中国語（簡体字）・韓国語・タイ語（画面右上で切り替え。初回はブラウザの言語設定に合わせ、対応していない言語の場合は英語。選んだ言語はブラウザに保存）

## 使い方

SigmaOmega は次の 3 つの方法で使えます。

- **オンライン**：<https://m-koga.github.io/sigmaomega/>（GitHub Pages。リリースごとに更新）。スマートフォンやパソコンでは、アプリとしてインストールできます（ホーム画面に追加、またはブラウザのメニューの「インストール」）。
- **ダウンロード**：各[リリース](https://github.com/m-koga/sigmaomega/releases)に、シミュレーター全体を 1 ファイルにした `index.html` があります。保存してブラウザで開きます。`sigmaomega-site-vX.Y.Z.zip` は、自分のサーバーに置くためのサイト一式（ページ、マニフェスト、アイコン）です。
- **ソースから**：`npm ci && npm run build` の後、`index.html` を開きます。

ページはフォントと数式表示（MathJax）をインターネットから読み込みます。接続がなくても動きますが、フォントはパソコンのものになり、数式は TeX の書き方のまま表示されます。

## 自動テスト

Node.js 22.18 以上が必要です。最初に一度 `npm install` を実行してください（型チェック用の TypeScript と、ブラウザのテスト用の Playwright がインストールされます）。

```
npm test           # index.html をビルドし、src/ts の型チェックをしてから、すべての単体テストを実行
npm run test:all   # 単体テストとブラウザでの操作テストの両方を実行
```

単体テストは、ページのスクリプトを `src/` から直接（起動処理の `src/ts/99-init.ts` を除き、型を取り除いて）読み込み、本物のページの代わりに用意した仮のオブジェクトの上で実行します。そのため、ビルドもブラウザも不要です。スクリプトの最上位の名前は、すべて型付きでテストから使えます（例：`api.S`、`api.simulate`。型は `npm run typecheck` が生成する `tests/app-api.d.ts`）。次のような実行方法も使えます。

```
node --test tests/simulation.test.ts              # 1 つのファイルだけ
node --test --test-name-pattern="root locus"      # 名前に一致するテストだけ
npm run test:watch                                 # 変更のたびに自動で再実行
```

### ブラウザでの操作テスト

ページそのものは、[Playwright](https://playwright.dev/) を使ってブラウザで操作して確認します（`ui/` フォルダ）。最初に一度だけインストールが必要です。

```
npm install
npx playwright install chromium    # Chrome または Chromium がインストール済みなら省略可
npm run test:ui
```

ブラウザは、Playwright でインストールしたものがあればそれを使い、なければインストール済みの Chrome や Chromium を自動で探します（`CHROME_PATH=/path/to/chrome` で指定も可能）。テストの前に `src/` から `index.html` を自動でビルドし、MathJax は `node_modules` から読み込むため、ネットワークなしで実行できます。テストは少なくとも 2 つずつ同時に動きます。各テストは保存領域が空の専用のブラウザ環境で、まず小さな `ui/start.html` を開き（新しい環境で最初に開いたローカルファイルのページが書いた保存内容は、再読み込みで失われることがあるため）、その後シミュレーターを 1 回だけ読み込みます。変更の作業中は関係するテストだけを動かし、公開前に一度すべてを実行します。次のような実行方法も使えます。

```
npx playwright test ui/layout.spec.ts            # 1 つのファイルだけ
npx playwright test -g "smartphone"              # 名前に一致するテストだけ
npx playwright test --headed                     # ブラウザの画面を表示して実行
npx playwright test --debug                      # 1 ステップずつ実行
npx playwright show-trace test-results/…/trace.zip   # 失敗したテストの記録を確認
```

### カバレッジ

```
npm run coverage            # 単体テストとブラウザのテスト
npm run coverage -- --unit  # 単体テストだけ（ブラウザ不要）
```

テストを実行しながら `src/ts/*.ts` のどの部分が実行されたかを記録し、ファイルごとの表を表示します。表には、単体テスト・ブラウザのテスト・両方を合わせたときに実行されたコードの文字数の割合と、行・関数の割合が出ます。一度も実行されなかった関数は `coverage/uncovered.txt` に、一度も実行されなかった行は `coverage/uncovered-lines.txt` に一覧が出ます（数値は `coverage/summary.json`）。版 1.73.6 では、テスト全体でコードの文字数の 98.0%、行の 98.9%、1018 個中 1009 個の関数が実行されます。ブラウザのテストは、スクリプトの文字を詰めずに残したページで実行します（`COV_DIR` が設定されていると `ui/global-setup.ts` がそのページを作ります。公開するページは詰めたもの）。終わったら `index.html` を作り直します。

機能を追加・変更したら `npm test`（画面に関わる変更では `npm run test:ui` も）を実行し、すべて成功することを確かめてから公開します。
GitHub に push すると、GitHub Actions（`.github/workflows/test.yml`）でも同じテストが自動で実行されます（版のタグを push するとリリースも始まります。`.github/workflows/release.yml`。「版の管理と更新履歴」を参照）。結果はリポジトリの「Actions」タブで確認できます。

### スクリプトの構成

```
利用者の操作 ──▶ S（設定） ──▶ update() ──▶ syncControls()            (17)  入力欄を S に合わせる
（19, 20, 24, 25 の          （18）          simulate(S)       (08)  ──▶ lastSim ─┐
  イベント）                                 freqResp(S)       (07)  ──▶ lastFr  ─┤  (06, setResults)
                                             computePZ(S)      (09)  ──▶ lastPZ  ─┼─▶ redraw() ──▶ drawTime, drawBode,
                                             sweepRuns(S)      (12)  ──▶ lastSweep┘   (18)         drawNyq, drawPZ (15, 16)
                                             renderSpecs/Tune/Sweep (17)              指標、余裕、表

```

ファイルは層に分かれていて、各ファイルは自分より下の層だけを使います（`tests/modules.test.ts` が確かめます）。

| ファイル | 層 | 内容 |
| --- | --- | --- |
| 01–04 | 基礎 | 更新履歴、翻訳（`T()`）、複素数と多項式、構文解析 |
| 05–06 | モデル | 定義の表。設定 `S`、そこから決まるもの（`ctrlRational`、`refValue` など）、最後の計算結果 |
| 07–12 | 計算 | 周波数応答、シミュレーション、ループと根軌跡、調整則、設計仕様、パラメータの掃引。ページには触れない |
| 13–14 | ページの基礎 | 要素（`$`、`byId`）、ファイルとメッセージ、ページの翻訳。表示の状態：レイアウト、表示する図、図の拡大、色 |
| 15–18 | 表示 | 図と極・零点配置の描画、パネルの内容と式。`update()` と `redraw()` |
| 19–29 | 操作 | 設定パネルとそのイベント、図の操作、書き出し、図の配置、ページのレイアウト、例題、メニューバー、ブロック線図の拡大、利用者マニュアル、言語の切り替え |
| 99 | 起動 | ページを組み立てる（単体テストでは読み込まない） |

下のファイルが上のファイルを呼ぶことはありません。表示の処理は `update()` を呼ばず、クリックで何をするかは操作の層で設定します（例：パラメータの掃引の表は `17-panels.ts` が描き、行のクリックは `19-controls.ts` の `buildSweep()` で一度だけ設定します）。

- `S`（`06-state.ts`、型 `State`）がすべての設定を持ちます。イベント処理は `S` を変えて `update()` を呼びます。`update()` はすべてを一度だけ計算し、結果を `lastSim`、`lastFr`、`lastPZ`、`lastSweep` に保持します。`redraw()` は、表示中の図をこれらの結果から描きます（拡大縮小、大きさ、図の表示など、見え方だけが変わったときにも呼ばれます）。
- 計算（ファイル 03–12：`08-simulation.ts`、`07-frequency.ts`、`06-state.ts` と `09-loop.ts` の伝達関数、`10-tuning.ts` のチューニング則、`11-specs.ts` の設計仕様、`12-sweep.ts` の掃引）はページに触れません。設定を最後の引数 `st`（省略時は `S`）で受け取り、結果を返します。別の設定で計算するときは、`simulate({ ...S, Kp: 4 })` のように写しを渡します。パラメータの掃引もこの方法で計算し、`S` を変えません。すべての計算が、写しを渡したときとグローバルな設定を変えたときで同じ結果になることを、`tests/state.test.ts` で確かめています。
- レイアウト（`layout`、`14-view.ts`。表示に反映するのは `24-layout.ts`）は設定とは別に扱います。ブラウザに保存され、例題と一緒に保存することもできます。

### 制御対象・制御器・調整則・グラフ・設計仕様・言語の追加

制御対象と制御器の種類、それらのパラメータ、調整則、グラフ、設計仕様、言語は、それぞれ 1 つの表で決まります。メニュー、入力欄、式、計算、ボタン、例題ファイルはこの表に従います。

- **制御対象**：`PLANTS` に項目を追加します。メニューの名前 `name`、パラメータ `p`、記号の式 `tex`、数値を入れた式 `texNum`、伝達関数 `tf`（分子・分母・むだ時間 `L`）、制御対象だけで不安定なら `unstable`（ナイキストの安定判別に使う）を書きます。
- **制御器**：`CONTROLLERS` に項目を追加します。メニューの名前 `label`、短い名前 `name`、パラメータ `p`、ループゲインを変えるときに掛けるパラメータ `gain`（根軌跡）、伝達関数 `rational` を書きます。`CTRL` と異なる初期値は `defaults` に書きます（P制御は K<sub>P</sub> = 1。制御器を切り替えたとき、前の制御器の初期値のままのパラメータは新しい制御器の初期値になり、手で変えた値はそのまま）。`kind: 'tf'` の制御器（位相進み・遅れ補償器など）は式 `texNum` も書きます。`kind: 'pid'` の制御器は並列形 PID のうち、ゲイン（`Kp`・`Ki`・`Kd`）がパラメータにある項を使い、2 自由度・y だけの微分・アンチワインドアップが使えます。
- **パラメータ**：新しいパラメータは `05-definitions.ts` の `PARAMS`（制御対象）か `CTRL`（制御器）に追加します。スライダー（`min`・`max`・`step`）、初期値 `val`、入力できる範囲 `hard`（どんな値でもよければ `[-BIG, BIG]`）、必要なら掃引と書き出すファイルで使う記号 `sym` と、パラメータ掃引の最初の値 `sweep`（ないときは今の値の ×0.5・×1・×2・×4）を書きます。新しい名前には `src/i18n.json` に訳が必要です。
- **調整則**：`10-tuning.ts` の `TUNE_RULES` に項目を追加します。メニューの名前 `label`、使う制御対象のモデル `model`（`'step'`：ステップ応答から求める反応曲線のモデル K・T・L、`'ult'`：限界ゲインと限界周期）、必要なもの（`needT`：時定数 T。積分器があると定義されない。`needDead`：見かけのむだ時間 L > 0）、P・PI・PID の標準形のゲイン（Kp・Ti・Td）を返す `gains` を書きます。係数の表で与える調整則は、Ziegler–Nichols 法や CHR 法のように `reactionRule()` を使えます。制御対象のゲインの符号と KP・KI・KD への換算は、すべての調整則で共通に行います。
- **グラフ**：`index.html` の `<div class="plot-wrap">` に canvas を置き（高さを変えるための `<div class="hgrip">` をその下に置く）、`05-definitions.ts` の `PLOTS` に項目を追加して、`update()` で描きます。項目には、表示名 `label`（領域を隠したときのつまみに出る）、PNG のファイル名 `file`、拡大縮小するか `zoom`、必要なら横軸を共有するグラフ `linkX` か縦横の縮尺をそろえる `keepAspect` を書きます。拡大縮小するグラフには、ホイールとドラッグでの拡大縮小と ＋ − Fit PNG のボタンが付きます。
- **設計仕様**：`05-definitions.ts` の `SPECS` に項目を追加します。表示名 `label`（≤ か ≥ で終わる）、単位 `unit`、入力できる最小の上限・下限 `low`、`bound`（`'max'`：測った値が限界以下、`'min'`：以上）、既定値（`on`・`v`）を書き、測り方を `11-specs.ts` の `SPEC_MEASURES` に書きます（ステップ応答の指標・周波数応答・閉ループ極から。当てはまらないときは `null`）。カードの行、既定値、判定、掃引の表の列、例題ファイルへの保存はこれに従います。図の上の線は `15-drawing.ts` で描きます。
- **言語**：`02-i18n.ts` の `LANGUAGES` に項目を追加します。ページの lang 属性 `tag`、メニューの名前 `name`、図のフォント `font`、利用者マニュアルと更新履歴の言語 `docs`（`'ja'` か `'en'`。`'en'` では英語で表示する旨の注記が出る）を書きます。`src/i18n.json` のすべての項目にその言語の訳を、`types.d.ts` の `I18nDict` にその言語のコードを、`index.html` の Google Fonts のリンクにフォントを追加します。
- 追加した項目は、テストを書かなくても `tests/kinds.test.ts` が確かめます。パラメータと範囲が定義されていること、式に数値が入ること、PID 型の伝達関数が周波数応答と一致すること、ループゲインで比例して変わること、ほかのすべての種類と組み合わせてシミュレーションと周波数応答が計算できること、各調整則が制御器の種類ごとにゲインを返し必要なものを確かめること、各グラフにファイル名と表示名があること、各パラメータの入力範囲がスライダーを含み掃引の値がその中にあること、各設計仕様に測り方と入力できる既定値があること、各言語がフォントとともにメニューにあることです。新しい言語の訳は `tests/i18n.test.ts` が求めます。

### コードの書き方

- TypeScript のファイルは [Prettier](https://prettier.io/) で整形しています（`.prettierrc.json`：1行120文字、文字列は単一引用符。Prettier の標準の TypeScript パーサーは TypeScript 7 にない JavaScript の API を必要とするため、Babel のパーサー `babel-ts` を使います）。コミットの前に `npm run format` を実行してください。GitHub Actions では `npm run format:check` で確認します。生成されるファイルは対象外です（`.prettierignore`）。
- 長い処理は、それぞれ1行の説明を付けた名前のある手順に分けています。例：`plot()`（枠の準備、目盛り線、軸の名前、補助線、曲線、凡例）、`drawPZ()`、`drawTime()`、`drawBode()`、`syncControls()`。描画の手順は、小さな「枠」のオブジェクト（`PlotFrame`、`PZFrame`：描画コンテキスト、描画領域、範囲、値から画素への変換）を共有します。
- コメントは独立した行か、説明する行の末尾に書き、コードの行の途中には書きません。

### TypeScript

- スクリプトは TypeScript で書き、`npm run typecheck`（`npm test` にも含まれる）で型をチェックします。ページそのものは、これまでどおり 1 つの JavaScript のファイルです。
- 使えるのは、取り除くだけで JavaScript になる書き方（型、interface、`as`、省略可能な引数など）だけです。`enum`、`namespace`、パラメータプロパティはエラーになります（`tsconfig.json` の `erasableSyntaxOnly`）。
- 各ファイルは ES モジュールです。使うものを他のファイルから import し（`import { S } from './06-state.ts'`）、他のファイルが使うものを export します。そのため、ファイルの依存関係は先頭を見れば分かり、import せずに使った名前は型エラーになります。型だけの import には `import type` を使います。どこでも使う型（`State`、`Poly` など）は `src/ts/types.d.ts` にあるグローバルな型で、import は不要です。
- import は型チェックのためのものです。ビルドは import の行と `export` を空白に置き換え、ファイル名の順に 1 つの通常のスクリプトにつなげます。そのためバンドラーは不要で、行と桁は `src/ts` と同じです。使える書き方は `import { … } from './NN-name.ts'` と、`function`・`const`・`let` の前の `export` だけです（それ以外は `npm run build` がエラーにします）。ファイル名の順は最上位のコードが実行される順です。各ファイルは番号の小さいファイルからだけ import します（`tests/modules.test.ts`）。そのため、ファイルは下から順に読むことができ、循環もありません。新しいファイルには、その層の番号を付けます。下のファイルが必要とするコードは、上のファイルから下のファイルに移します。
- 変数を変更できるのは、それを宣言したファイルだけです（import した変数には代入できません）。他のファイルからは、そのファイルの小さな関数（`setResults()`、`setLayout()`、`setShownPanels()`、`resetPZView()`、`setLangCode()` など）を呼びます。
- 要素は `$(id)` で取り出します。`$` はページに実在する id だけを受け付け、要素の型も返します（`$('Tsim')` は `HTMLInputElement`、`$('cvY')` は `HTMLCanvasElement`）。id の打ち間違いや、canvas に対する `.value` などは型エラーになります。`` $(`in-${k}`) `` のようにスクリプトで組み立てる id は、HTML に書かれた id のパターン（`id="in-${k}"`）と照合されます。ページの実行時にしか決まらない id（`data-` 属性やオブジェクトのキーから得るもの）には `byId(id)`（要素の型を指定するときは `byId<HTMLCanvasElement>(id)`）を使います。
- id を持つ要素を追加したときは、`npm run build`（または `npm test`）を実行して `src/ts/element-ids.d.ts` に反映します。古いままだと `npm run check` で検出されます。
- すべての関数と変数に型を付け、`noImplicitAny` を有効にしています。新しく書くコードにも型が必要です。共通の型は `src/ts/types.d.ts` にあります：状態 `State`、レイアウト `Layout`、例題 `Scenario`、多項式 `Poly`、複素数 `Complex`、伝達関数 `TF`・`Rational`、シミュレーションの結果 `SimResult`、周波数応答 `FreqResult`、極・零点 `PZResult`、掃引の各回 `SweepRun`、設計仕様の判定 `SpecEval`、グラフの設定 `PlotOptions`、数値の設定項目のキー `NumKey`。
- `any` を意図して使っているのは、MathJax、アーティファクトのビューアーの API、ファイル・リンク・テキストから読み込む例題データの検査（`scMerge`、`scLayout`。どんな内容でもあり得るため）だけです。
- `strictNullChecks` を有効にしています。`null` や `undefined` になり得る値（まだシミュレーションしていない、省略可能な項目、`data-` 属性など）は、使う前に確認する必要があります。必ず存在するものには `19-controls.ts` の補助関数を使います：CSS セレクターで探すページの要素には `qs(セレクター, 探す範囲)`、canvas の描画コンテキストには `ctx2d(canvas)`、その他には `must(値, 説明)`。見つからないときは、後で「null のプロパティを読めない」と失敗する代わりに、何がないかを示すエラーを出します。
- 成功か失敗のどちらかになる結果は、共用体型（union）で表しています。`err` を確かめると、TypeScript がどちらかを判断します（例：`10-tuning.ts` の `TuneResult`。`if(r.err!==undefined)` ならエラー、そうでなければゲイン）。
- ビルド用のプログラム、単体テスト、ブラウザのテストも TypeScript で書いています。これらは ES モジュール（`package.json` の `"type": "module"`）で、Node.js と Playwright がビルドなしで直接実行します。ファイル内の import では `.ts` ファイル名を書き（`import { fresh } from './harness.ts'`）、型だけの import には `import type` を使います。型チェックには `tsconfig.node.json` を使い、`src/ts` も含めているため、テストからページのスクリプトの型が分かります：`fresh().simulate()` は `SimResult` で、ブラウザのテストで `page.evaluate()` に渡すコードでも `S` や `$('bodeS')` などページの名前を型付きで使えます。
- テストでは、`defined(x)`（null や undefined であってはならない値）と `success(r)`（エラーであってはならない自動調整の結果）が、条件を満たさないときに分かりやすいメッセージでテストを失敗させ、型も絞り込みます。`boxOf(page, セレクター)` は、表示されているはずの要素の位置を返します。
- すべての厳密なチェックを有効にしています（2つの tsconfig の `"strict": true`）。これで TypeScript への移行は完了です。`catch` で受け取るエラーの型は `unknown` なので、`errMessage(e)` と `errCode(e)`（`19-controls.ts`）で読み取ります。

## 版の管理と更新履歴

- 版番号は `src/ts/01-changelog.ts` の `CHANGELOG` 配列の先頭の版で、画面右上に表示されます（`npm run build` で `<meta name="version">` にも書き込まれます）。
- 新しい版は `CHANGELOG` 配列の先頭に追加し、`en` に英語、`ja` に日本語の項目を書きます。
- 更新履歴のファイルは `npm run docs` で生成します：[CHANGELOG.md](CHANGELOG.md)（英語）、[CHANGELOG.ja.md](CHANGELOG.ja.md)（日本語）。引用情報の [CITATION.cff](CITATION.cff)（最新の版番号と日付）も同時に作ります。直接編集しないでください。
- README は英語版（[README.md](README.md)）と日本語版（このファイル）があります。内容を変えたときは両方を更新してください。
- **リリース。** 開発者が手で、最新の版のタグを push してリリースします：`git tag v1.73.5 && git push origin v1.73.5`。すると `.github/workflows/release.yml` が、タグが更新履歴の最新の版であることを確かめ、単体テストを実行し、`index.html` とサイト一式の zip を添えた GitHub のリリースを作ります。リリースの説明は更新履歴から英語と日本語で作ります（`node scripts/gen-docs.ts --notes`）。GitHub Pages の公開元が GitHub Actions に設定されていれば（Settings › Pages › Source: GitHub Actions）、続けて同じワークフローを `main` でそのタグについて動かし、タグの版のサイト（`npm run pages`）を <https://m-koga.github.io/sigmaomega/> に配置します（`github-pages` の環境はタグからの配置を許さず、`main` からだけ許すため）。設定されていなければ、この手順は飛ばします。ワークフローを手で実行すると（Actions › Release › Run workflow）、リリースを作らずに現在の `main`、または *tag* に指定した版のタグを Pages に配置します。
- **DOI。** リポジトリを公開した後、[Zenodo](https://zenodo.org/) と連携すると（GitHub でログインし、リポジトリをオンにする）、リリースごとに DOI が付きます。Zenodo は `CITATION.cff` を読み取ります。
